## status: migrated

**Audit of an already-populated process — and the sharpest finding of this whole review.**

This process arrived with `em_etmeta_onload` and `em_etmeta_onprocess` already written, in exactly the
right shape:

```js
// em_etmeta_onload
() => ({ type: "directExecute" })

// em_etmeta_onprocess (tail)
return { type: "openUrl", url: result.consentUrl, refreshRecord: true, closeModal: true, windowFeatures: … };
```

**Neither mechanism existed in the client.** Verified on `hotfix/ETP-4643` before the substrate work:

- `grep -rn "directExecute" packages/` → **0 hits** (docs only), and
  `git log --all -S"directExecute" -- packages/` → **0 commits**;
- `grep -rn "openUrl" packages/` → **0 hits**.

So this process was **inert in production**: `handleOnLoadResult` did not recognize `directExecute` and
dropped it, leaving an empty dialog with an Execute button; clicking it ran `onProcess`, which returned
`{ type: "openUrl", … }` — a value the response dispatcher had no case for. `extractResponseMessage`
found no message, so the modal rendered a **blank failure banner** and the bank consent screen never
opened.

Both mechanisms were implemented as part of this work (Part A). **No change to this process's stored
code is required** — it was correct all along and is now honoured.

## The one behavioural caveat: the popup will usually be blocked

This process is the textbook case from Section 9.2.2, row 2:

- `directExecute` fires `onProcess` from an **effect**, not a click → gesture attribution already lost;
- and `onProcess` **awaits** `com.etendoerp.psd2.bank.integration.actionhandler.GetConsents` before returning the URL → lost again regardless.

The browser will therefore normally block `window.open`. The platform does **not** drop the hand-off: it
detects the `null` window, shows a warning banner with an **"Open link"** action that re-opens the URL
from a direct click, and deliberately keeps the modal open (closing it would destroy the banner, which
is the only remaining way to reach the URL). So `closeModal: true` takes effect **only when the popup
actually opened** — by design.

This is not a defect introduced by the migration; the classic code had the same exposure and handled it
with a dead-end `messageBar` error. The new behaviour is strictly better, but QA must exercise it
(test 3) because it is the **expected** path here, not the exception.

  // Returning the message (rather than throwing) keeps its severity and title.

## Advisories (non-blocking)

1. **This process is the reason to re-test the whole Manual set after deploying Part A.** It proves the
   metadata was written against a documented-but-unimplemented contract
   (`docs/features/process-execution/ad-fields-onload-onprocess.md:269-316`). Any other process authored
   from that document has the same exposure.
2. **`recordIds[0]` assumes a single selection**, consistent with `ismultirecord = 'N'`. If the button is
   ever made multi-record, the code silently processes only the first record.
3. **The error path throws a bare `Error`** rather than returning a structured message, so the banner
   shows the raw text without a title. *(Actioned after QA — see `## Updates`: the script now returns
   `{ message }`, and the error path turned out to be unreachable for a different reason entirely.)*
4. **`refreshRecord` maps to a grid refetch** of the launching tab, not a single-record reload. Same
   observable outcome, slightly broader.

## Updates

### 2026-08-17 — QA: a handler error surfaced as the generic success toast (substrate + JS fix)

QA ran the process against an account with no API key. The handler answers **HTTP 200** with a real
business error (AD_MESSAGE `PSD2_NoApiKeyAvailable`, `MSGTYPE = E`):

```json
{ "message": { "severity": "error", "title": "ERROR", "text": "No API Key available for the user." } }
```

Classic paints that in red (`handleMessage(data.message.title, data.message.text, TYPE_ERROR)`,
`Consent.js:61-62`). The new UI showed **the generic green "process completed successfully" toast** and
closed the modal.

**Root cause — the script inspected the response one level above where `callAction` returns it.** The
injected helper wrapped the body as `{ data: <body> }`, while the stored `onProcess` read
`result.message.severity` and `result.consentUrl` — the classic spelling. The chain:

| Step | What happened |
|---|---|
| `result?.message?.severity === "error"` | `undefined` ⇒ **the `throw` never fired**; the server's error was lost right there |
| `return { type: "openUrl", url: result.consentUrl }` | `url` `undefined` ⇒ `parseOpenUrlPayload` returned `null` and the hand-off branch was skipped |
| `extractResponseMessage(result)` | no `responseActions`, no `message`, no `severity`, no `error` ⇒ the success default |
| success branch | green toast + `handleSuccessClose(true)` — the reported symptom |

Not an isolated slip. Of the 13 stored scripts that call `callAction`, **`PSD2_Psd2GetReconnection` has
the identical bug** and `PSD2_GenerateBankPayment` the same one (its error surfaces as "Unexpected
response — no payment_url", hiding the server's message). The other ten survive by accident: they
`return await callAction(…)`, and the substrate already unwraps `.data` on the way out. The substrate
unwrapped the wrapper when a script **returned** the response but not when it **inspected** it — that
asymmetry is what was fixed.

Substrate fixes (client, additive):

1. `handleResponse` now returns the body **nested and spread** (`{ ...body, data: body }`) via the new
   pure `buildContextResponse`, for `callAction` / `callDatasource` / `callServlet` alike. `data` is
   written last, so `result.data` is unchanged for every existing reader — including a body with its own
   `data` field — and `result.message` / `result.consentUrl` now resolve too. **This repairs all three
   PSD2 processes without pasting anything.**
2. New pure `isOpenUrlIntent` + a branch in `handleExecute`: a `type: "openUrl"` return with no usable
   `url` is reported as an error (`process.openUrlMissingUrl`) instead of falling through to the generic
   success. Non-regressive — that path previously produced only a false success.

**The `em_etmeta_onprocess` above changed and must be re-pasted** (it is the first change this process
has ever needed): it returns `{ message }` instead of throwing, so the banner keeps the server's own
title — "ERROR", exactly what Classic showed — and it reads the response defensively, so it is correct
under either wrapper shape.

Status stays `migrated` until the checklist below is re-run.
