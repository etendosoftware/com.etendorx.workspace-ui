### Why `directExecute`

Classic acts on the button click itself. `directExecute` reproduces that — no dialog, no Execute
button. The popup-blocker concern that originally argued against it did not survive QA: the tab opens
after the `await`, and if a stricter browser ever blocked it, the platform's "Open link" banner is
reachable in direct-execute mode (substrate fix, see `## Updates`).

## Advisories (non-blocking)

1. **The URL must never go through `/api/erp/`.** *(Rewritten after QA — the original advisory guessed
   the proxy would work; it does not. See `## Updates` for the measurements.)* The Swagger page has to be
   served from its real Classic path, and `erpHosted: true` is what guarantees that.
2. **No extra click.** *(Rewritten after QA.)* `directExecute` reproduces Classic's click-to-open, and the
   popup-blocked fallback is reachable in that mode.
3. **No AD message to create.** *(Rewritten after QA.)* `OB.Utilities.showSuccess` does not exist in the
   ERP and the classic call is guarded, so **Classic shows no message at all**. The faithful port shows
   none either — the previously proposed `ETAPI_SwaggerOpening` label is not needed and must not be
   created.
4. **Empty selection is tolerated, as in Classic.** With nothing selected, `name` is `""` and Swagger
   opens unfiltered. Reproduced deliberately rather than "fixed".

## Manual-test checklist

1. **(Most important.)** Open the **OpenAPI Flow** window, select a flow, press **Open Swagger**. → The
   tab opens **without any Execute click** and **the Swagger UI actually renders**, filtered to the
   selected flow. A 401 JSON body, a login page or an empty Swagger shell all mean the URL or the session
   is wrong.
2. Confirm the opened URL is `<classic-host>/web/com.etendoerp.openapi/?tag=<flow name>` — the same one
   Classic opens — with the tag URL-encoded. Pick a flow whose name contains a space or an accent to

3. Confirm **no banner and no toast** appear: Classic shows nothing here.
4. Confirm the tab was **not** blocked by the popup blocker. If a warning banner with an **"Open link"**

5. Run with **no** row selected. → Swagger opens unfiltered (`?tag=`), matching Classic.
6. **No regression:** run an external `openUrl` process (PSD2 *Get Consents*) and confirm its URL opens
   exactly as before.

## Updates

### 2026-08-17 — first QA run: wrong URL, invented message, extra click (substrate + JS fix)

QA reported three things: the modal opens empty, **Execute** opens
`http://localhost:3000/api/erp/web/com.etendoerp.openapi?tag=BulkTaskCreatorFlow` (not the link Classic
opens), and the modal shows a banner reading `ETAPI_SwaggerOpening`.

**Defect 1 — the URL targeted the proxy.** Advisory 1 had flagged this as unverified; it is now measured,
and it fails for three independent reasons:

| Check | Result |
|---|---|
| `GET :3000/api/erp/web/com.etendoerp.openapi/?tag=X` | **308** — Next.js strips the trailing slash, which is exactly the URL QA saw |
| `GET :3000/api/erp/web/com.etendoerp.openapi?tag=X` | **401** `{"error":"Unauthorized - Missing Bearer token"}` — the proxy is an API and `window.open` sends cookies only. **This is what the user saw in the tab.** |
| `index.html:23-26` | The page derives its spec endpoint from `window.location`: `contextPath = pathname.substring(0, pathname.indexOf('/',1))`. Under `/api/erp/…` that yields `/api` ⇒ it would fetch `/api/ws/com.etendoerp.openapi.openAPIController` ⇒ 404 |

So the page only works from its real Classic path (`:8080/etendodev/web/com.etendoerp.openapi/` → **200**),
and because `…/ws/com.etendoerp.openapi.openAPIController` is **401** without a session, the tab also
needs a live Classic session.

**Defect 2 — the message never existed.** `grep -rn "showSuccess"` over the whole ERP returns nothing:
`OB.Utilities.showSuccess` is undefined, and `etapi-swagger.js:28` calls it inside
`typeof … === "function"`. **Classic shows no message.** The migration substituted a `messageBar` call
using a label that does not exist either (`ad_message` ⇒ 0 rows), hence the raw key on screen.

**Defect 3 — the extra click**, plus a latent trap: in `directExecute` mode the modal renders only the
bare overlay, which does **not** host `ProcessMessageBar`. A blocked popup would therefore have left the
user on a spinner with the "Open link" banner invisible.

Substrate fixes (client, additive):

1. `openUrl` gained an optional `erpHosted` flag plus the pure `resolveErpHostedUrl`
   (`utils/processes/definition/openUrl.ts`). Marked payloads are expanded against
   `config.etendoClassicHost` and routed through `/meta/legacy/redirect`, which validates the JWT, primes
   a Classic session and redirects to the real Classic path — fixing both halves of defect 1. Unmarked
   payloads are returned untouched, so the four external `openUrl` processes are unaffected.
2. `shouldRenderDirectExecuteOverlay` takes an optional `hasMessage`, and the modal subscribes to the
   message-bar store: the chrome returns as soon as a message exists. This also rescues
   `PSD2_Psd2GetConsents` and `PSD2_Psd2GetReconnection` from the same dead end.

**The generated code above changed and must be re-pasted**: `em_etmeta_onload` (new, `directExecute`) and
`em_etmeta_onprocess` (ERP-relative URL + `erpHosted` + `closeModal`, and the `messageBar` line removed).

### 2026-08-17 — second QA run: the URL opens, but the modal never closes (substrate fix)

QA confirmed the tab now opens on the button click, at the right URL. One blocker left: coming back to
the app, an un-dismissable modal showed a spinner and the text "Open Swagger".

Root cause, substrate only. The script *did* ask to close (`closeModal: true`) and the dispatcher *did*
call it, but the modal's `handleClose` opens with `if (isPending) return;` — a guard meant to stop a
**user** from abandoning a running process by clicking the X. An `openUrl` dispatches from *inside*
`handleExecute`'s `startTransition`, so `isPending` is always `true` there and the programmatic close was
always refused. In direct-execute mode there is no chrome either, so nothing could dismiss it by hand.

Fix: split the two paths. `performClose` (unconditional) is what the dispatch context receives;
`handleClose` keeps the pending guard for the X, the footer buttons and the backdrop. This also repairs
`PSD2_Psd2GetConsents` and `PSD2_Psd2GetReconnection`, which use the same `directExecute` + `openUrl` +
`closeModal` shape and were stuck the same way.

**No re-paste**: the metadata above is already correct.

Status stays `migrated` until the checklist above is re-run.
