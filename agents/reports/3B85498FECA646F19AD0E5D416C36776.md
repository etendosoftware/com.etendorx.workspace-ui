## The three blockers, ranked *(as first assessed, 2026-08-10)*

> Superseded in part: blocker 3 was resolved on 2026-08-18, blocker 1 has a decided approach, and a
> fourth blocker (CORS) was found on 2026-08-19. Kept for the record; read `## Updates` for current state.

1. **The provider/scope chooser is a bespoke DOM component, not a form.** This is the substantive one.
   The classic UI is a visual grid: one card per provider, each with an icon button per scope, tooltips
   from `description`, and a divider. `openDynamicForm` can render *a choice*, not *this*.
2. **The two-phase popup cannot be reproduced.** Classic deliberately opens a blank window during the
   click and navigates it after `getAccount()` resolves. `openUrl` has no "reserve now, navigate later"
   mode, so the popup is opened post-`await` and will be blocked; the user recovers through the fallback
   banner. Functionally reachable, behaviourally different.
3. **`OB.User.id` is missing** — same root gap as `ETRXGetToken`
   (`DDADF2E25EEF444A80208E681EFF24CD.md`). Without it the `state` payload cannot bind the token to a
   user.

## A degraded migration is possible — but it is a product decision, not a translation

> **Considered and rejected, 2026-08-19.** The team saw the real modal and chose the custom-component
> path instead (`## Updates`). This section is kept because it documents the fallback that exists if the
> component work is ever deprioritized — not as the recommended route.

If the team accepts losing the visual chooser, the process **can** be expressed as:

- `onLoad` → `{ type: "directExecute" }`;
- `onProcess` → `callServlet` the `/available-providers` endpoint, flatten providers × scopes into a
  single `LIST` field (`label: "<Provider> — <scope name>"`), `openDynamicForm` it, `callAction`
  `GetSSOProperties` for the account, and `return { type: "openUrl", … }`.

That yields: **no icons, no descriptions, no provider grouping, and a popup that the browser will
normally block** (recovered by the "Open link" banner). It is a materially different interaction, so it
is **not** emitted here. If the team wants it, say so explicitly and it will be produced as a documented
deviation — that is the team's call, not this agent's.

## What would unblock a faithful migration

1. A **component schema for a card/option-grid picker** (icon + label + description per option, grouped),
   renderable from an `onLoad` return under `etmetaCustomComponent = 'Y'` — the same channel
   `warehouseProcess` uses today (Section 9.1), which is currently hard-wired to that single schema type.
   A schema registry would generalize it.
2. A **"reserve a window now, navigate it later"** primitive — e.g. `openUrl` accepting a
   `reserveBeforeAwait: true` hint, or an explicit `reserveWindow()` the script calls before its first
   `await`.
3. **Session user identity** exposed to scripts (see `DDADF2E25EEF444A80208E681EFF24CD.md`).

**Current state of that list (2026-08-19, after implementation):** item 1 is **done** — the schema
registry was generalized and `MiddlewareTokenProcess` registered against it. Item 2 turned out **not to
be a requirement at all**: it only constrains scripts going through `openUrl`, and a component owns its
own click handler (see `### 2026-08-19 — implementation`). It should be struck from
`F355D9A73F554AF5860A532D92C167EC` as a shared requirement too. Item 3 is **done**. The fourth
requirement discovered later — a server-side route to the provider list, around the middleware's
missing CORS headers — is **done** via `SSOProviderListActionHandler`.

## Generated code per field

`em_etmeta_custom_component` — **`Y`**. Without it the schema is discarded silently and an empty
dialog renders (`customComponentUtils.ts:35-38`); the flag is what selects this execution path.

`em_etmeta_onload`:

```js
async (_processDefinition, { selectedRecords }) => {
  // Always answer with a middlewareTokenProcess schema, carrying any failure inside it: the modal
  // does not read the hook's error channel, so a throwing onLoad would render an empty dialog.
  // Failures travel as a stable code — the component owns the translated wording.
  const base = {
    type: "middlewareTokenProcess",
    providers: {},
    accountId: "",
    redirectUri: "",
    startEndpoint: "",
  };

  const record = selectedRecords?.[0];
  if (!record) {
    return { ...base, errorCode: "noRecordSelected" };
  }

  // The middleware serves /available-providers without CORS headers, so the browser cannot read it.
  // This handler performs the call server-side and returns the account id in the same round trip,
  // which is what lets the component open its popup without any await inside the click.
  const response = await callAction("com.etendoerp.metadata.SSOProviderListActionHandler", {
    etrxOauthProviderId: record.id,
  });

  if (response?.status !== "Success") {
    return {
      ...base,
      errorCode: response?.errorCode || "unreachable",
      errorMessage: response?.message || "",
    };
  }

  return {
    ...base,
    providers: response.providers || {},
    accountId: response.accountId || "",
    redirectUri: response.redirectUri || "",
    startEndpoint: response.startEndpoint || "",
  };
}
```

### Why the error travels inside the schema

`ProcessDefinitionModal` destructures `schema`, `payscriptPlugin`, `effectiveOnProcess` and `loading`
from `useWarehousePlugin` — **not `error`**. An `onLoad` that throws therefore leaves the modal falling
through to its standard render: an empty parameter dialog with nothing to explain itself. Returning a
well-formed schema that carries the failure keeps it visible without touching the modal's error
plumbing, which is the non-regressive option.

### Why the error is a code, not a message

`errorCode` is a stable identifier (`noRecordSelected`, `noProviderId`, `providerNotFound`,
`noEndpoint`, `unreadableResponse`, `unreachable`) that the component maps to a translated string in
`ComponentLibrary/src/locales/{en,es}.ts`. The English `message` the handler sends alongside it is a
diagnostic for logs and support and is **never displayed**. An unknown code degrades to the generic
`unreachable` wording rather than surfacing the raw identifier, so adding a code server-side can never
render an untranslated token to the user.

### 2026-08-19 — decision: migrate through the custom-component path, not through metadata

**What was decided.** The team opened the real modal in a running Classic instance (Chrome with web
security disabled, to work around blocker 4 below) and concluded that reconstructing this dialog from
`openDynamicForm` field descriptors is not worth doing. The chosen route is the **custom-component
path**:

- set `em_etmeta_custom_component = 'Y'` on this process;
- have `em_etmeta_onload` return a schema describing the provider/scope chooser;
- render it with a **new, purpose-built React component** in the client, mapped from that schema.

This is the same channel `GenericWarehouseProcess` uses (Section 9.1). Note the gate in
`customComponentUtils.ts:35-38` accepts only `true` or `'Y'`, and it is declarative: with the flag unset
the schema is silently discarded and an empty dialog renders, with no console or server error. That
failure mode is documented in `40317268E74C445FA85DB97249AFFE37.md`, which hit it in production.

**Why this is the right call rather than a shortcut.** The classic dialog is a two-level visual grid —
provider card → icon button per scope, with the scope `description` as tooltip. `openDynamicForm`
renders `TEXT`/`CHECK`/`LIST` only (`parameterDialogStore.ts:43`); the message bar cannot carry it
either, since its DOMPurify allowlist forbids `<img>` and `<a>` and is deliberately neither exported nor
parameterizable (`sanitizeHtml.ts:30-38`). There is no metadata shape that expresses this dialog. A
component is the honest answer.

**Scope note for whoever picks this up.** Today the schema registry is hard-wired to the single
`warehouseProcess` type. Adding a second type is the first task, and it is shared-substrate work — it
should be designed so a third schema costs nothing, rather than special-casing this process.

**Not done in this phase.** No component, no schema type, no `em_etmeta_*` value. `em_etmeta_*` columns
stay `LEAVE EMPTY` and `em_etmeta_custom_component` stays `NULL` until the component exists — setting
the flag early would produce exactly the empty-dialog failure described above.

### 2026-08-19 — blocker 4 (new): the providers endpoint is unreachable from any browser (CORS)

**Symptom.** With a correctly created `EtendoMiddleware` provider record, clicking **Get Middleware
Token** in Classic fails immediately with *"Error fetching providers. Providers can't be loaded. Contact
the system administrator"* — the generic `.catch()` at `:156-162`.

**It is not a permissions problem**, despite what the message suggests. Verified from the command line:

```
GET https://sso.etendo.cloud/oauth-integrations/available-providers
→ HTTP 200, 636 bytes of valid JSON (1 provider: google; 2 scopes: Drive Edit / Drive Read Only)
→ response headers: content-type, x-content-type-options — and nothing else
```

No `Access-Control-Allow-Origin`, tested against four origins (`http://localhost:8080`,
`https://sso.etendo.cloud`, `https://demo.etendo.cloud`, `null`) — so it is not an allowlist miss, the
service simply does not emit CORS headers. `OPTIONS` answers `Allow: GET,HEAD` with no
`Access-Control-*` either. The request is a simple GET, so no preflight is sent: the browser issues it,
the server answers 200, and the browser then discards the response and rejects the promise.

**This blocks the migrated version too, whichever shape it takes.** The fetch originates in the browser
regardless of which UI hosts it, and the new UI runs on a different origin, so the outcome is identical.
Using `callServlet` would be worse, not better: it adds `Authorization` and `X-CSRF-Token` headers,
which turns the request into a preflighted one that the server would reject at the `OPTIONS` stage.

**Two possible fixes:**

1. Enable CORS on `sso.etendo.cloud` for instance origins — owned by the middleware team, outside this
   repo.
2. **Proxy the provider list through the ERP** — a small servlet in `com.etendoerp.etendorx`, or an
   extension of `GetSSOProperties` to return the provider list alongside `account`. This removes the
   dependency entirely and also covers instances whose users' browsers have no direct internet egress.
   Option 2 is the one that makes this process migratable without waiting on anyone.

**Consequence for the component design:** the new component should read its provider list from an
ERP-side call, not from a direct browser fetch to the middleware. Worth settling before the schema is
designed, since it determines whether `onLoad` can populate the schema in one round trip.

### 2026-08-19 — QA observations from the real Classic modal

- **The chooser is much smaller than assumed.** The middleware currently returns **one provider
  (`google`) with two scopes** (`drive.file` — Edit Access, and `drive.readonly` — Read Only). The
  original report weighed the degraded `LIST` option against a possibly large, hard-to-navigate grid;
  at this size that argument mostly evaporates. Recorded because it makes the fallback in *"A degraded
  migration is possible"* far more defensible than it looked in August, should the component work slip.
- **Scope icons are externally hosted** (`img.icons8.com`). Any component reproducing the visual chooser
  inherits that dependency, and with it a third-party host that can fail or be blocked. Consider
  bundling icons or degrading gracefully when the image 404s.
- **The flow past the chooser is intact.** `GET .../start?provider=google&account_id=…&scope=…
  &redirect_uri=…&state=…` answers `302` to `accounts.google.com/o/oauth2/v2/auth` with the middleware's
  own `client_id`. Only the provider-list step is broken.
- **Environment blocker for end-to-end QA (not a code issue).** After consent, the flow failed with a
  `500` from the middleware. Etendo's own access logs show `saveTokenMiddleware` has **never** been
  requested — zero hits across every log since 2025-11-17 — so the callback never reached the ERP and
  the error is server-side at `sso.etendo.cloud`. Most likely this dev instance's System Identifier
  (`ad_system_info.system_identifier`, sent as `account_id`) is not registered with the shared
  middleware; `redirect_uri` pointing at `localhost` is the other candidate. Either way it blocks
  obtaining a real token, and therefore also blocks QA of `F355D9A73F554AF5860A532D92C167EC`

### 2026-08-19 — implementation

The process is migrated. What changed against the plan the earlier entries sketched:

**Blocker 2 dissolved; no new substrate primitive was built.** The report treated "reserve a window
now, navigate it later" as a missing platform capability, and listed it as a requirement shared with
`F355D9A73F554AF5860A532D92C167EC`. That framing was right for a *script* returning
`{ type: "openUrl" }`: the dispatcher opens the window after the `await`, outside the user-gesture
window, so the browser blocks it. It does not apply here. A custom component's `onClick` is ordinary
React code, so `window.open` can be called synchronously — and because the account id now arrives with
the schema, **there is no `await` inside the click at all**. The popup opens once, already pointed at
its final URL. That is strictly simpler than Classic, which opens a blank window and navigates it after
`getAccount()` resolves (`:98-131`). **The shared requirement can be struck from both reports.**

**Blocker 4 (CORS) resolved server-side.** New `com.etendoerp.metadata.SSOProviderListActionHandler`
(`@ApplicationScoped extends BaseActionHandler`; kernel action handlers are resolved by CDI from the
`_action` class name, so no `ad_model_object` row is needed — verified against
`AttributeSetInstanceActionHandler` and `GetSSOProperties`, neither of which has one). It resolves the
provider record by id, reads `authorizationEndpoint` **from the database** — never from the request, so
there is no way to aim it at an arbitrary host — performs the GET with explicit timeouts, and returns
the catalogue together with `accountId` and `redirectUri`. Failures answer
`{ status: "Error", message }` rather than throwing, so the component can show the reason.

It lives in `com.etendoerp.metadata` because `com.etendoerp.etendorx` ships as a jar with no sources in
the workspace. That is also the right home: `SSOService.exchangeCodeForToken` already makes outbound
HTTPS calls from this module, so the dependency is not a new one.

**Absorbing `GetSSOProperties`.** Disassembling `etendorx-4.2.0.jar` confirmed that
`GetSSOProperties` with `properties=account` returns `SystemInfo.getSystemIdentifier()`. Returning the
same value from the new handler removes a round trip — and with it the `await` that forced the
two-phase popup. Worth recording for anyone tempted to call it directly: `GetSSOProperties` reads
`content` at the **root**, not from `_params`, so through `createCallAction` it would need
`_topLevel: true`. Reading the wrong level fails silently into a false success.

**The registry is now general.** The custom-component channel was hard-wired to `warehouseProcess` in
two places: the guard in `useWarehousePlugin` that decided whether an `onLoad` result was usable, and
the branch in `ProcessDefinitionModal` that picked the component. Both now consult
`Custom/registry.ts`. Registering a schema type is the entire cost of adding a third component.
Non-regressive by construction: `warehouseProcess` stays registered, and an unregistered `type` is
still discarded silently into the standard render, exactly as before. `getCustomComponent` uses
`Object.hasOwn`, so a schema whose `type` is `"constructor"` cannot resolve to an inherited `Object`
member and be handed to React.

**Two small robustness fixes over Classic**, both deliberate:

- `crypto.randomUUID` only exists in a secure context. On an instance served over plain HTTP from a
  host other than localhost it is `undefined` and the Classic button throws, doing nothing. The state
  only has to be unique and opaque — the middleware answers with its own signed state — so
  `middlewareTokenUtils.randomState` falls back to `crypto.getRandomValues`.
- `ETRX_PopupNotBeOpened` has **no row in `ad_message`** (verified), so both `OB.I18N.getLabel` and the
  new UI's `getLabel` echo the raw key. The component uses local text plus a real "Open link" anchor
  instead of propagating that bug into an `alert` with no way forward. The other six labels the handler
  uses do exist and are read normally.

**Files.** Backend: `SSOProviderListActionHandler.java` + `SSOProviderListActionHandlerTest.java`
(the outbound call and the account id are overridable, so every branch runs without network or AD).
Client: `Custom/registry.ts`, `Custom/types.ts`, `Custom/MiddlewareTokenProcess/*`; edits to
`useWarehousePlugin.ts`, `ProcessDefinitionModal.tsx` and `imports.ts`.

**Verification.** `tsc --noEmit` clean; Biome clean on the new files; the full `ProcessModal` Jest

### 2026-08-19 — all user-facing text moved to the locale files

The first cut of the component read its labels from `ad_message` via `getLabel`, mirroring Classic, and
hardcoded one English string for the popup-blocked case. Both are now wrong for this codebase: the new
UI's convention is `ComponentLibrary/src/locales/{en,es}.ts`, which is what `GenericWarehouseProcess`
and the rest of `ProcessModal` already use.

Everything the dialog renders now lives under `processModal.middlewareToken` in **both** locale files.
The popup-blocked notice reuses the platform's existing `process.popupBlocked` rather than introducing
a second phrasing for a situation the platform already has wording for, and the recovery anchor reuses
`process.openLink`.

**The error contract changed as part of this.** `SSOProviderListActionHandler` previously returned
English prose in `message`; it now also returns a stable `errorCode`, and the `onLoad` forwards it as
`errorCode` (with `errorMessage` kept purely as a diagnostic). The component maps the code to a
translated string through an explicit literal map, so the keys stay type-checked, and an unrecognised
code degrades to the generic `unreachable` wording instead of leaking the identifier to the user.
Adding a code on the server can therefore never render an untranslated token in the UI.

**Trade-off worth knowing.** Reading from the locale files rather than `ad_message` means an ERP
administrator can no longer retranslate this dialog from the Application Dictionary — the strings ship
with the client bundle. That is the deliberate new-UI convention, and it also removes the failure mode
that produced this process's own bug: `ETRX_PopupNotBeOpened` has no `ad_message` row, so Classic
displays the raw key. The six labels that do exist in `ad_message` are unaffected there; Classic keeps
using them.
