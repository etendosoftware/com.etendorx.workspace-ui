## The one behavioural caveat: the popup will usually be blocked

This process is the textbook case from Section 9.2.2, row 2:

- `directExecute` fires `onProcess` from an **effect**, not a click → gesture attribution already lost;
- and `onProcess` **awaits** `com.etendoerp.psd2.bank.integration.actionhandler.ReconnectConnection` before returning the URL → lost again regardless.

The browser will therefore normally block `window.open`. The platform does **not** drop the hand-off: it
detects the `null` window, shows a warning banner with an **"Open link"** action that re-opens the URL
from a direct click, and deliberately keeps the modal open (closing it would destroy the banner, which
is the only remaining way to reach the URL). So `closeModal: true` takes effect **only when the popup
actually opened** — by design.

**Unlike its sibling, the classic code here does *not* have the same exposure** — and that is worth
stating plainly. `Reconnect.js:44-60` opens the popup **synchronously, before the server call**
(`window.open('')`, then `popup.location.href = data.reconnectUrl` in the callback) precisely to keep the
user gesture. The declarative `openUrl` hand-off cannot reproduce that: the URL is only known after the
`await`. So this is a genuine behavioural difference, mitigated — not erased — by the platform's
"Open link" fallback banner, which QA must exercise (test 3) because it is the **expected** path here.

```js
async (processDefinition, payload) => {
  // callAction exposes the body nested (`.data`) and spread; accept either form.
  const response = await callAction("com.etendoerp.psd2.bank.integration.actionhandler.ReconnectConnection",
    { _topLevel: true, id: payload.recordIds[0] }
  );
  const result = response?.data ?? response;

  // Classic (Reconnect.js:73-81) reports the handler's message and skips the popup
  // in TWO cases: an error, and a success carrying no reconnectUrl (nothing to
  // reconnect). Returning the message keeps the server's severity AND title.
  const message = result?.message;
  const isError = message?.severity === "error";
  const isEmptySuccess = message?.severity === "success" && !result?.reconnectUrl;
  if (isError || isEmptySuccess) {
    return { message };
  }
  if (!result?.reconnectUrl) {
    return { message: { severity: "error", text: "ReconnectConnection returned no URL" } };
  }

  return {
    type: "openUrl",
    url: result.reconnectUrl,
    refreshRecord: true,
    closeModal: true,
    windowFeatures: `width=${Math.round(screen.width * 0.7)},height=${Math.round(screen.height * 0.7)},left=${Math.round(screen.width * 0.15)},top=${Math.round(screen.height * 0.15)}`
  };
}
```

## Advisories (non-blocking)

1. **This process is the reason to re-test the whole Manual set after deploying Part A.** It proves the
   metadata was written against a documented-but-unimplemented contract
   (`docs/features/process-execution/ad-fields-onload-onprocess.md:269-316`). Any other process authored
   from that document has the same exposure.
2. **`recordIds[0]` assumes a single selection**, consistent with `ismultirecord = 'N'`. If the button is
   ever made multi-record, the code silently processes only the first record.
3. **The error path throws a bare `Error`** rather than returning a structured message, so the banner
   shows the raw text without a title. *(Actioned after the sibling process's QA — see `## Updates`.)*
4. **`refreshRecord` maps to a grid refetch** of the launching tab, not a single-record reload. Same
   observable outcome, slightly broader.

## Manual-test checklist

1. Open the window backing `PSD2_Finacc_Connection.Reconnect_Conn`, select a financial account connection, and press **PSD2 Get Reconnection**.
   → **No empty dialog and no Execute click**: a loading overlay appears immediately and the process
   runs. (Before Part A this showed an empty dialog — that regression must be gone.)
2. If the browser allows the popup: the bank's reconnection page opens in a new window sized to ~70% of
   the screen, the modal closes, and the launching grid refreshes.
3. **If the browser blocks the popup (the expected path):** a **warning banner** appears with an
   **"Open link"** button, and **the modal stays open**. Click "Open link" → the reconnection page opens.
   Confirm the modal did *not* close and the banner was still reachable.
4. Force a server error (e.g. a connection whose status is not Inactive → `PSD2_ReconnectOnlyWhenInactive`).
   → A **red banner** with the server's own title and text; no green toast, and the modal stays open and
   closable.
5. **The success-without-URL case** (the branch classic has and the stored code had dropped): a connection
   the handler answers `severity: "success"` for with no `reconnectUrl`. → A **success** message carrying
   the server's title and text, and **no** window opens. It must not appear as an error.
6. Reopen the process after a successful run. → It runs again cleanly (the one-shot direct-execute guard
   is re-armed on close, so no dead overlay).
7. Confirm the launching grid reflects the new reconnection state after returning from the bank.

## Updates

### 2026-08-17 — carried over from the sibling's QA: the handler's message was being swallowed

QA of `PSD2_Psd2GetConsents` (`C580B3B6…`) found that the injected `callAction` returns the response body
wrapped as `{ data: <body> }`, while these PSD2 scripts read it at the classic level (`result.message`,
`result.reconnectUrl`). Both came back `undefined`, so the error guard never fired, the URL was empty, and
the substrate reported the generic success toast. **This process has the identical defect** — it was found
by inspection here, not by QA, so it has not been observed on screen yet.

The substrate fix (`handleResponse` now exposes the body nested **and** spread) repairs the reading level
with no paste. Two things still needed a JS change, and they are the reason to re-paste:

1. **Classic's success-without-URL branch was never ported.** `Reconnect.js:73-81` reports the handler's
   message and skips the popup for an error **or** for `severity: "success"` with no `reconnectUrl` — the
   stored code only ported the error half. Left as it was, that case would now hit the substrate's new
   "openUrl with no url" guard and show an **error** where classic shows a **success** message. That is a
   regression the substrate cannot fix on its own: only the script knows the handler's severity is
   authoritative here.
2. **The error path threw a bare `Error`** (advisory 3), which carries only a string, so the handler's
   `title` was lost and the banner fell back to the generic "Process failed". Returning `{ message }`
   keeps severity and title, exactly as classic's `setMessage(TYPE, message.title, message.text)`.

`em_etmeta_onload` is unchanged. Status stays `migrated` until the checklist above is run.
