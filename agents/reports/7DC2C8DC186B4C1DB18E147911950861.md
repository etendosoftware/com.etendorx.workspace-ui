## The honest middle ground (requires approval)

There is real evidence that the tree behaviour is **already degraded in Classic**:

- `showTreePopupWindow: false` (:223),
- `this.characteristicCombos[i].getField(0).setIcons([])` with the comment
  *"TODO: Remove popup icon because currently the popup does not load any data (see issue 28887)"* (:250-251),
- the server already ships a complete `valueMap` per characteristic (:199).

If the popup icon is dead and the value map is complete, the field is in practice **a combo backed by
`valueMap`** — which `LIST` reproduces exactly, losing only **type-ahead substring filtering**.

So a degraded migration would be: `onLoad` → `directExecute`; `onProcess` → `callAction` `INITIALIZE`,
map `productCharList` to one `LIST` field each (`refList` from `valueMap`, `defaultValue` from
`selectedValue`), `openDynamicForm` them all in one dialog, rebuild `updatedValues` /
`existingProdChValues` from the collected values, `callAction` `UPDATE`, then message + `refreshGrid`.

**What is lost:** type-ahead filtering, and any tree hierarchy if `valueMap` turns out to be flat while
the real value set is not. **What must be verified first** (neither is answerable from the source):

1. Does `UpdateInvariantCharacteristicsHandler` return a `valueMap` containing **every** selectable
   characteristic value, or only a first page?
2. How many values does a realistic characteristic have? A plain select is fine for 10 and unusable for
   500.

Answer those two and say the word, and the degraded version will be produced as an explicitly documented
deviation.

## What would unblock a faithful migration

- **A datasource-backed field type in `openDynamicForm`** — e.g. `inputType: 'SELECTOR'` with
  `{ targetEntity, displayField, valueField, textMatchStyle }`, reusing the standard selector components
  the process form already renders for `_id_19` / tree references. `ParameterDialogHost` already routes
  each field through `ProcessParameterSelector`, so most of the machinery exists; what is missing is a
  descriptor shape for it and the datasource plumbing.
- Optionally, **tree-reference support** in that field type (`treeReferenceId`, `parentCharId`,
  `productCharSubsetId`) for full parity.

### `em_etmeta_payscript_logic` — `obuiapp_process`

```js
// @module-scope
// Mirrors OB.ProductCharacteristics.execute + isc.UpdateInvariantCharacteristicsPopup
// (productCharacteristicsProcess.js:23 and :66): fetch the invariant characteristics,
// let the user pick a value for each from a LIST, post the updates, report, refresh.
const ACTION_HANDLER = "org.openbravo.client.application.event.UpdateInvariantCharacteristicsHandler";

// Classic's NO_SUBSET sentinel (UpdateInvariantCharacteristicsHandler.java:59):
// "-1" means this product characteristic has no Characteristic Subset configured.
const NO_SUBSET = "-1";
// Upper bound for the subset fetch. A subset is a curated shortlist, so this is a
// safety valve rather than an expected limit.
const SUBSET_FETCH_LIMIT = 1000;

// SmartClient value maps are { value: label } objects; a LIST field takes [{ value, label }].
const toRefList = (valueMap) => {
  if (Array.isArray(valueMap)) return valueMap;
  return Object.entries(valueMap ?? {}).map(([value, label]) => ({ value, label: String(label) }));
};

// Reads the characteristic values a Characteristic Subset allows, reproducing the
// filter Classic applies through the tree reference's where clause (AD_REF_TREE
// 95582A51651D415993D0FD3B64C8E861). The handler's valueMap is NOT subset-filtered
// — the subset arrives as a separate field precisely because Classic applies it in
// the datasource — so without this the dialog would offer values Classic refuses,
// and the UPDATE branch persists them without validating.
// Resolves to null on any failure: fail open, keeping the unfiltered list. That is
// never worse than not filtering at all, and never leaves an empty dialog.
const fetchSubsetValueIds = (subsetId) =>
  new Promise((resolve) => {
    try {
      OB.Datasource.create({
        entity: "CharacteristicSubsetValue",
        requestProperties: { params: { _startRow: 0, _endRow: SUBSET_FETCH_LIMIT } },
      }).fetchData([{ fieldName: "characteristicSubset", operator: "equals", value: subsetId }], (response, data) => {
        if (response.status < 0 || !Array.isArray(data)) {
          console.warn("[UpdateInvariants] subset fetch failed; offering every value", subsetId, response.status);
          resolve(null);
          return;
        }
        resolve(data.map((row) => row.characteristicValue).filter(Boolean));
      });
    } catch (error) {
      console.warn("[UpdateInvariants] subset fetch threw; offering every value", error);
      resolve(null);
    }
  });

// Restricts a characteristic's options to its subset, always keeping the blank entry
// the handler adds (valueMap[""] = ""), which is the only way to clear a value.
const applySubset = (refList, allowedIds) => {
  if (!allowedIds) return refList;
  const allowed = new Set(allowedIds);
  return refList.filter((option) => option.value === "" || allowed.has(option.value));
};

const buildField = async (characteristic) => {
  const subsetId = characteristic.productCharSubsetId;
  const allowedIds = subsetId && subsetId !== NO_SUBSET ? await fetchSubsetValueIds(subsetId) : null;
  return {
    // The characteristic id doubles as the form key: react-hook-form reads "." and
    // "[]" in a key as a nested path, so a name carrying either (e.g. "Talla U.S.")
    // would make setValue write somewhere the collector never reads, silently
    // returning the seeded default instead of the user's choice.
    id: characteristic.id,
    name: characteristic.id,
    // Classic titles the field with the raw `title`; `name` is the slash-sanitised
    // internal key (handler line 106), which must not reach the user.
    label: characteristic.title,
    inputType: "LIST",
    refList: applySubset(toRefList(characteristic.valueMap), allowedIds),
    defaultValue: characteristic.selectedValue,
  };
};

const runUpdateInvariants = async (productId) => {
  const init = await callAction(ACTION_HANDLER, { productId, action: "INITIALIZE" });
  const characteristicList = init?.data?.productCharList ?? [];

  const existingProdChValueByCharId = {};
  for (const characteristic of characteristicList) {
    existingProdChValueByCharId[characteristic.id] = characteristic.existingProdChValue;
  }
  const fields = await Promise.all(characteristicList.map(buildField));

  const collected = await openDynamicForm({ title: "Update Characteristics", fields });
  // Cancel: classic closes the popup and posts nothing.
  if (!collected) return { type: "closeModal" };

  const updatedValues = {};
  const existingProdChValues = {};
  for (const item of collected) {
    updatedValues[item.id] = item.value;
    existingProdChValues[item.id] = existingProdChValueByCharId[item.id];
  }

  const response = await callAction(ACTION_HANDLER, {
    productId,
    updatedValues,
    existingProdChValues,
    action: "UPDATE",
  });

  const message = response?.data?.message ?? {};
  return {
    message: { msgType: message.severity, msgText: message.text },
    responseActions: [{ refreshGrid: {} }],
  };
};

return { runUpdateInvariants };
```

## Updates

### 2026-08-18 — unblocked: degraded `LIST` migration generated, additive, no substrate changes

**What was verified before generating code.** The original report gated the degraded path behind two
open questions and explicit approval ("it is a product decision, not a translation, so it is not emitted
unilaterally"). Both were resolved against source this session:

1. **Is `valueMap` complete, or paginated?** `UpdateInvariantCharacteristicsHandler.java:108-117`
   (`INITIALIZE` branch) calls `characteristic.getCharacteristic().getCharacteristicValueList()` — every
   `CharacteristicValue` row for the characteristic, no `Restrictions`, no limit — and puts every one into
   the `valueMap` returned to the client, plus an explicit `"" → ""` entry so the field can be cleared.
   **Complete and unpaginated**, confirmed by reading the handler directly, not inferred.
2. **How many values does a realistic characteristic have?** Still not answerable from source (a business
   data question), but no longer load-bearing: since the `valueMap` is always complete, a large value
   count only makes the generated `LIST` long, never wrong.

**A stronger finding than the report anticipated.** Reading
`ob-formitem-tree.js:26-72` (`OBTreeItem.init`) shows the picker icon and the full-screen `treeWindow`
popup (`isc.OBTreeItemPopupWindow`, with its own search grid) are **only constructed when
`showTreePopupWindow !== false`**. `productCharacteristicsProcess.js:223` passes
`showTreePopupWindow: false` for every characteristic field, and `:251` additionally strips the icon
(`setIcons([])`, the `issue 28887` `TODO` the original report already flagged). Net effect: **Classic
itself never opens any popup, tree browser, or selector grid for this field today.** The only surviving
interactive capability is the inline dropdown (`this.tree`, an `OBTreeItemTree`, always constructed
regardless of `showTreePopupWindow`) that appears while typing and filters by substring against the
`CharacteristicValue` datasource. So the "faithful migration" this report's "what would unblock" section
imagined — full tree navigation, pick list, selector grid — is not actually reachable in the running
application; the honest target was narrower than originally framed.

**Legacy-popup delegation does not apply.** Investigated whether the `LegacySelectorAffix` /
`LegacyProcessServlet` mechanism (built for delegating a Classic Search-reference info-window popup into
an iframe/popup from the new UI) could give this field full parity instead. It cannot, for two independent
reasons: (a) `LegacyProcessResolver.resolveSearchPopupUrl` only resolves a URL for `AD_Model_Implementation`
rows with `action = 'S'` (Search references) — this field's reference is a tree-reference, a different
kind, and no Classic info-window page exists for it to point at; (b) the resolution
(`FieldBuilder.addLegacySearchUrl` → `getSelectorInfo`) only ever runs for real `AD_Process_Para`/`AD_Field`
rows (`ParameterBuilder`, `ProcessParameterBuilder`, `FieldBuilderWithColumn`) — this process has **zero**
`obuiapp_parameter` rows, so that backend computation never executes for it, and `DynamicFormField` (the
`openDynamicForm` descriptor) has no `selector` field or fourth `inputType` to carry the result even if it
did.

**Why the degraded `LIST` migration is now the accepted shape, not a stopgap.** Given the above, `LIST`
populated from the complete `valueMap` loses only substring type-ahead — the one real capability Classic
still offers beyond a plain combo — and nothing else. The code generated above is a direct reuse of the
`directExecute` + `openDynamicForm` + dynamically-built `LIST` fields shape already shipped in
`A832A5DA28FB4BB391BDE883E928DFC5.md` (Open Close Periods), generalized from one field to N. No file
under `packages/MainUI/utils/processes/` or `packages/MainUI/components/ProcessModal/` was touched —
zero substrate changes, fully additive.

**Status is `migrated`, not `qa-passed`**, until the manual-test checklist above is run.

### 2026-08-19 — post-QA review: two defects fixed, one advisory retracted

A first manual pass reported the process working. Reviewing the substrate that actually renders the
dialog turned up two real defects in the code above and one false claim in this report. All three are
now addressed.

**Retracted: type-ahead filtering was never lost.** The previous entry and advisory 7 claimed the `LIST`
gives up substring filtering. That is wrong. `ProcessParameterSelector` routes `case "list"` to
`components/Form/FormView/selectors/ListSelector`, which wraps `Select`, and `Select` carries its own
search box:

```js
const filteredOptions = useMemo(
  () => options.filter((option) => option.label.toLowerCase().includes(searchTerm.toLowerCase())),
  [options, searchTerm]
);
```

Classic filtered server-side against the datasource; the new UI filters client-side over the complete
option list. Same visible result. Preselection is fine too — `Select` syncs its label from
`options.find(o => o.id === selectedValue)` against the default `ParameterDialogHost` seeds. The
coverage-table row for `textMatchStyle` is reclassified from `unsupported` to `supported`.

**Defect 1 — the form key silently discarded the user's choice.** The field key was
`characteristic.name`. React Hook Form parses `.` and `[]` in a key as a nested path, so for a
characteristic named e.g. `Talla U.S.` the round trip broke. Reproduced against the installed RHF:

```
1) defaults sembrados : {"Talla U.S.":"ID-DEL-VALOR-ACTUAL"}
2) watch(name)        : ID-DEL-VALOR-ACTUAL          ← preselection still works
3) tras setValue      : {"Talla U.S.":"ID-DEL-VALOR-ACTUAL",
                         "Talla U":{"S":"ID-ELEGIDO-POR-EL-USUARIO"}}   ← writes nested
4) collectValues lee  : ID-DEL-VALOR-ACTUAL          ← returns the OLD value
```

The user picks a new value, confirms, sees a success banner, and the **previous** value is re-saved. No
error anywhere. Classic is immune because SmartClient's `values` is a flat object. Note this has nothing
to do with duplicate names — a single `.` in a unique name is enough.

Fixed by keying the field on `characteristic.id` (a UUID, structurally safe) and moving the display text
to a new optional `label`. This also makes the old duplicate-name advisory moot.

**Substrate change (additive) enabling the fix.** `DynamicFormField` gained an optional `label`
(`packages/MainUI/utils/processes/definition/parameterDialogStore.ts`), and `ParameterDialogHost` turns
the declared labels into a `labelOverrides` map passed to `ProcessParameterSelector`
(`packages/MainUI/components/ProcessModal/ParameterDialogHost.tsx`). `labelOverrides` is a pre-existing

**Defect 2 — Characteristic Subset was ignored.** The classic tree filters its options through the tree
reference's where clause (`AD_REF_TREE` `95582A51651D415993D0FD3B64C8E861`):

```sql
e.characteristic.id = @parentCharId@
and ('-1' = @productCharSubsetId@
     or e.id in (select cs.characteristicValue.id
                 from CharacteristicSubsetValue cs
                 where cs.characteristicSubset.id = @productCharSubsetId@))
```

The handler's `valueMap` is **not** subset-filtered — it returns every value of the characteristic
(`getCharacteristicValueList()`, line 109) and ships `productCharSubsetId` as a separate field precisely
because Classic applies it in the datasource, not in the handler. Building the `LIST` from `valueMap`
therefore offered values Classic refuses, and the `UPDATE` branch persists whatever id it receives
without validating against the subset — no server-side check exists anywhere. That made the new UI able
to create data the old UI could not.

Fixed in the script: when `productCharSubsetId !== "-1"` it queries `CharacteristicSubsetValue` through
`OB.Datasource` (the same api-client path grids and selectors use) and intersects with the `valueMap`,
always preserving the blank entry so clearing a value still works. The query **fails open** — any error
resolves to `null` and the unfiltered list is kept, which is never worse than today's behaviour and never
leaves an empty dialog — and logs a `[UpdateInvariants] subset fetch failed` console warning.

**This path is unverified against live data.** `etendodev` has 21 `M_Product_Ch` rows and **zero** with a
subset, so there was nothing to exercise it with. Manual test 9 explains how to build the data and what
the console warning means. Everything else in the checklist is unaffected.
