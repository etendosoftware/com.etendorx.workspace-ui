## The classic flow (three steps)

1. `openClose` sets `actionHandler`, `adTabId`, `processId`, then `execute` collects the selected period
   ids and opens `isc.OpenClosePeriodProcessPopup`.
2. The popup's `getActionList` calls `OpenClosePeriodHandler` with `action: 'ACTION_COMBO'` and fills the
   single `Action` field from `response.data.actionComboBox.valueMap` / `.defaultValue`, stashing
   `response.data.nextStepId` on the field as `closePeriodStepId`.
3. OK posts `{ closePeriodStepId, recordIdList, action }` to the same handler, shows `data.message` in
   the launching tab's banner, closes the popup and refreshes the view.

This is precisely the `openDynamicForm` + `LIST` shape.

### `em_etmeta_payscript_logic` — `obuiapp_process`

```js
// @module-scope
// Mirrors OB.OpenClose.execute + isc.OpenClosePeriodProcessPopup
// (periodControlStatus.js:95 and :130): fetch the action combo, ask the user,
// post the choice, report, refresh.
const ACTION_HANDLER = "org.openbravo.client.application.event.OpenClosePeriodHandler";
const ACTION_FIELD = "action";

// SmartClient value maps are { value: label } objects; a LIST field takes
// [{ value, label }]. Tolerates the array form in case the handler changes.
const toRefList = (valueMap) => {
  if (Array.isArray(valueMap)) return valueMap;
  return Object.entries(valueMap ?? {}).map(([value, label]) => ({ value, label: String(label) }));
};

const runOpenClose = async (recordIds) => {
  const combo = await callAction(ACTION_HANDLER, { recordIdList: recordIds, action: "ACTION_COMBO" });
  const data = combo?.data;
  if (!data) {
    return { error: { msgText: OB.I18N.getLabel("OBUIAPP_ErrorInProcess"), msgType: "error" } };
  }

  const refList = toRefList(data.actionComboBox?.valueMap);
  // Classic sets defaultToFirstOption on the field, so an absent default still
  // arrives at the dialog preselected.
  const defaultValue = data.actionComboBox?.defaultValue ?? refList[0]?.value;

  const collected = await openDynamicForm({
    title: "Process Request",
    fields: [
      {
        name: ACTION_FIELD,
        inputType: "LIST",
        refList,
        defaultValue,
      },
    ],
  });
  // Cancel: classic closes the popup and posts nothing.
  if (!collected) return { type: "closeModal" };

  const response = await callAction(ACTION_HANDLER, {
    closePeriodStepId: data.nextStepId,
    recordIdList: recordIds,
    action: collected[0]?.value,
  });

  const message = response?.data?.message ?? {};
  return {
    message: { msgType: message.severity, msgText: message.text },
    responseActions: [{ refreshGrid: {} }],
  };
};

return { runOpenClose };
```

## Advisories (non-blocking)

1. **`valueMap` shape is the one runtime assumption.** SmartClient `setValueMap` accepts either a
   `{ value: label }` object or a plain array. `OpenClosePeriodHandler` emits the object form, which
   `toRefList` converts; the array form is handled too. If the dialog shows options labelled with raw
   ids, this conversion is what to inspect (manual test 2).
2. **Popup title kept verbatim.** Classic calls `popup.setTitle('Process Request')` with a hardcoded,
   untranslated English string (:157). Reproduced as-is rather than silently introducing a label. If a
   translated title is wanted, create an AD message and swap the `title:` value — a one-line change.
3. **The grid cell renderers in this file are out of scope.** `PeriodControlStatus_Field` and
   `PeriodStatus_Field` (:19-90) are `isc.Label` subclasses bound through `AD_FIELD.CLIENTCLASS` on the
   `C_Period` / `C_PeriodControl` grids (`6F0F218E…`, `905ACA2D…`, `DD1EBE37…`, `E9A00524…`). They are
   **not** part of this process and have no `em_etmeta_*` channel. If the coloured period-status cells
   are required in the new UI, track them as separate work — this is unchanged from the 2026-06-16 report.
4. **`adTabId` plumbing dropped.** Classic threads `params.adTabId` through so the callback can find the
   right view's message bar (`view.getView(params.adTabId).messageBar`). The new UI has one banner per
   modal, already scoped correctly, so three lines of plumbing disappear.
5. **`validationMessage` / `validationOK` are dead** in `execute` (:99 — declared, never used). Dropped
   per playbook Section 10.3.
6. **Two launching columns, one migration.** Both `C_Period.OpenClose` and `C_PeriodControl.OpenClose`
   point at this process id, so pasting the code once covers both entry points. Both must be QA'd
   (manual tests 1 and 6) because the selection shape differs.

## Manual-test checklist

1. Open the **Fiscal Calendar → Period** tab, select **one** period, press **Open/Close Period**.
   → No empty dialog and no Execute click: a dialog titled **"Process Request"** appears directly, with a
   single **Action** select.
2. Inspect the select's options. → They are the human-readable labels the handler returns (e.g.
   *Open Period* / *Close Period*), **not** raw ids or `[object Object]`. If they are raw, see advisory 1.
3. Confirm one option is **preselected** on open (classic `defaultToFirstOption` + the handler's
   `defaultValue`).
4. Press **Cancel**. → The dialog closes, no banner appears, and the period status is unchanged.
5. Repeat, choose an action and press **Confirm**. → The banner shows the handler's message with its own
   severity, and the grid refreshes so the new period status is visible without a manual reload.
6. Repeat tests 1–5 from the **Period Control** tab (`C_PeriodControl.OpenClose`), which is the second
   launching column.
7. Select **several** periods and run it. → One `ACTION_COMBO` call for the whole selection, and the OK
   post carries **all** selected ids in `recordIdList`.
8. Run it on a period whose status makes the action invalid. → The handler's error message shows in the
   banner and the modal stays open.
9. Run with **no** selection. → An error message appears instead of an `ACTION_COMBO` call with an empty
   list.
