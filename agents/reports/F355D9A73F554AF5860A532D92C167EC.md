**child window the script owns for the whole flow** — it writes HTML into that window, drives it through
several states, and then waits for the window to `postMessage` a result back. The metadata hook model
has no window handle, no cross-document write, and no listener that outlives `onProcess`.

## Why this is not a "degraded migration" candidate

Unlike `ETRXGetMiddlewareToken` (`3B85498FECA646F19AD0E5D416C36776.md`), there is no lesser version worth
shipping. Strip the unsupported parts and what remains is "open the picker URL in a tab" — the user
picks a document, and **nothing happens**, because the result comes back via `postMessage` to a listener
that cannot exist. The document is never approved. That is not a degraded feature; it is a broken one
that looks like it works, which is precisely what the gate protects against.

## What would unblock this

All three are required; any one alone is insufficient.

1. **A retained-window primitive.** `openUrl` returning a handle, or a `reserveWindow()` the script calls
   before its first `await` and navigates later — this also unblocks blocker 2 of
   `3B85498FECA646F19AD0E5D416C36776.md`.
2. **A cross-window message channel** owned by the platform: e.g. a script-facing
   `awaitWindowMessage({ origin, type })` returning a Promise, so the origin check and listener teardown
   stay in the substrate instead of leaking into migrated JS. Migrated scripts must never register raw
   `window` listeners — they would outlive the modal and leak.
3. **A way to render status inside the child window** (the `popupRenderLoading` / `popupRenderError`
   states), or an accepted product decision to drop that feedback and show it in the parent's message
   bar instead.

A cleaner alternative worth considering before building all of the above: **move the handshake
server-side**, so the picker posts to an ERP endpoint and the process becomes a plain AR-2 `openUrl` plus
a grid refresh. That would make this process trivially migratable and is likely less work than the three
platform primitives above.

## Advisories (non-blocking)

1. **The `<a href>` origin fallback (:181-189) is dead code** in every browser the new UI supports; drop
   it whenever this is migrated (playbook Section 10.3).
2. **The `message` listener is never removed** in the classic code — each run adds another. Any future
   platform primitive must own teardown rather than reproducing this leak.
3. **`this` is not the view.** `this?.processOwnerView?.messageBar` relies on SmartClient call-site
   binding and is defensively optional-chained precisely because it is often `undefined`. In the new UI
   the banner is the top-level `messageBar`, so the ceremony disappears.
4. **Two `.js` files, one process.** The `<path>` for this process is a trampoline; the substance is in
   `google-picker.js`. Recorded here so a future run does not migrate the 4-line file and declare victory.

## Updates

### 2026-08-18 — re-verified against source; confirmed `blocked`, no migration attempted

Re-read `google-picker.js` line by line against this report's coverage table. All three `unsupported`
mechanisms hold; one line reference in the table is corrected:

- The deferred navigation on the retained window is `popup.location.replace(url)` at **`:234`**, not
  `:174+` as written above — `:174` is where the `url` variable is built, not where it is used. The
  mechanism and its `unsupported` classification are unchanged (it is still "reserve the window
  synchronously, `await` a server round-trip, then navigate the already-open window").
- `:96` (`window.open('about:blank', 'GooglePicker', …)`), `:2-56` (`popupRenderLoading` /
  `popupRenderError` writing into the child document), and `:191-232` (`window.addEventListener` with
  `{ once: true }`, gated on `evt.origin`, handling `PICKER_SUCCESS`) all confirmed as described.

**Why this stays `blocked` rather than getting a plan.** The three missing primitives this report asks
for — a retained-window handle, a platform-owned cross-window message channel, and a way to render
state inside the child window — do not exist anywhere in the client codebase today (confirmed:
`packages/MainUI/utils/processes/definition/openUrl.ts:146-163`'s `openExternalWindow` opens a window
and returns only a `boolean`, discarding the handle; no `reserveWindow`/`awaitWindowMessage` equivalent
exists under `utils/processes/`). Building them is a shared-substrate change touching the `openUrl`
contract and/or a new message-channel primitive used by every AR-2 process, not an additive,
process-local fix — exactly the kind of change this project's standing instructions call for
discussing before attempting. This session, the same retained-window primitive was already on the
table for the sibling process below and the decision was explicitly **not** to build it now.

The other path this report names — moving the picker's result handshake server-side, so it posts to an
ERP endpoint instead of `postMessage`-ing the opener — is a `com.etendoerp.etendorx` (ERP/Java) change,
not a client migration, and was not explored this session either.

**Relationship to `3B85498FECA646F19AD0E5D416C36776` (GetMiddlewareToken) confirmed.** Both processes
share blocker #1 (retained window / deferred navigation) and remain `blocked` for the same underlying
reason. Any future work on a retained-window primitive should be scoped to unblock both at once rather
than solved twice.

**No code changed.** `em_etmeta_*` columns stay `LEAVE EMPTY`; `## status: blocked` is unchanged; no
other file, report, or guide section was touched.

### 2026-08-19 — decision: **wont-migrate** (out of scope)

**The decision.** The process is not used in the system, and will not be migrated. `em_etmeta_*` columns
stay `LEAVE EMPTY` permanently. No further work is planned on it.

**What tipped it.** A Classic baseline run (details below) confirmed something the static analysis had
already spotted but had not weighed heavily enough: **the process does not approve anything, even in
Classic.** The trampoline calls the implementation with no arguments —

```js
// approveGoogleDoc-picker.js
OB.ETRX.approveGoogleDoc = function () {
  OB.ETRX.openGooglePickerPopup();   // ← no processEndpointName, no ssoBaseFromArg
};
```

— so `processEndpointName` is `undefined`, the `payload?.processEndpoint` branch at
`google-picker.js:195-223` is unreachable, and every successful pick falls through to the `else` at
`:224`, which only writes *"File authorized and successfully processed"* into the message bar. The
document is never posted anywhere. The post-processing call exists in the file but nothing wires it up.

That reframes the cost/benefit completely. The report previously argued for three new platform
primitives (retained window, cross-window message channel, child-window rendering) or an ERP-side
rework of the handshake. All of that would be spent reproducing a flow whose observable effect is a
success message.

**What is preserved and why.** The coverage table, the three unblock requirements and the "not a
degraded-migration candidate" reasoning stay untouched. Two reasons: they are still accurate, and
**requirement 1 (a retained-window / deferred-navigation primitive) is shared with
`3B85498FECA646F19AD0E5D416C36776`**, which is still in scope. Whoever builds that primitive should read
this report for the second use case, even though this process will not consume it.

**Environment note.** End-to-end QA of the Classic original was only possible after working around an
unrelated infrastructure problem — this dev instance is not registered with `sso.etendo.cloud`, so the
real token flow returns `500` at the middleware callback. The token used for the baseline run was
minted manually and injected through the `saveTokenMiddleware` servlet; the procedure is recorded in
`3B85498FECA646F19AD0E5D416C36776.md` → `## Updates`. Not a property of this process, but the reason
its checklist could be exercised at all.

**Two findings worth keeping, both outside this migration's scope:**

1. **The launching button is hidden.** `ETRX_Token_Info.Approve_Google_Doc` has `isdisplayed = 'N'` on
   the *Token Info* tab of the *oAuth Provider* window (`ad_field`, seqno 70) — the only tab that
   carries it. The process therefore has **no visible entry point in the standard UI**; the button had
   to be enabled in the Application Dictionary to test it at all. This corroborates the "not used"
   assessment.
2. **Tokens are stored in plaintext.** `SaveTokenFromMiddleware` calls `setToken(access_token)` and
   persists it directly; the stored value in `etrx_token_info.token` is the raw Google access token
   (verified: 253 chars, `ya29.a…` prefix). The official documentation states `ETRXTokenInfo` /
   `ETRXTokenUser` encrypt tokens at rest with AES-256-GCM, which does not match observed behaviour in
   `etendorx-4.2.0`. Harmless locally; on a production instance it means read access to that table is
   live access to users' Drive accounts. **Raised for the RX team — unrelated to this migration.**
