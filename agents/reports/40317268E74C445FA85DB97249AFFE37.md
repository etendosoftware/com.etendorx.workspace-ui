## This is a special case: the custom-component rendering path

Almost every process in this report set renders the **standard metadata-driven parameter form** — a flat
list of fields built from `OBUIAPP_Parameter` rows. Validate Picking List does not, and cannot: its
Classic UI is a full pick-and-validate station (`isc.OBPickValidateProcess` — barcode input, quantity
spinner, a scrollable grid with an inline-editable *Verified* column and a per-row status icon) that has
no expression as a list of parameters. It has **zero `OBUIAPP_Parameter` rows**.

So it takes the path described in `new-ui-js-migration-guide` §9.1: `onLoad` returns a **schema** that
describes a bespoke UI, and the new UI renders `GenericWarehouseProcess` from that schema instead of the
parameter form.

**That path is opt-in, and the opt-in is a database flag, not code.**

```
EM_Etmeta_Custom_Component = 'Y'   →  onLoad's schema renders GenericWarehouseProcess
EM_Etmeta_Custom_Component = NULL  →  the schema is silently discarded; an empty dialog renders
```

The gate is `usesCustomComponent()`
(`Custom/GenericWarehouseProcess/customComponentUtils.ts:35-38`), which accepts `true` or `'Y'` only.
The flag is deliberately declarative: `useWarehousePlugin` will **not** speculatively run a process's
`onLoad` just to discover whether it returns a custom schema, because doing so would execute every
standard process's `onLoad` inside the reduced warehouse sandbox. So an unset flag is indistinguishable
from "this is an ordinary process", and the failure is silent — no console error, no server error, just a
dialog with nothing in it.

### Why it did not render before

With the flag unset:

1. `useWarehousePlugin` short-circuits and never evaluates the schema-returning `onLoad`;
2. the **standard** `onLoad` path runs instead and hands the returned schema to
   `updateParametersFromOnLoadResult`, which does not know the key `type`, so it is dropped;
3. `renderParameters()` returns `null` (zero parameters), leaving an **empty dialog** with a live
   Execute button.

The flag was set manually through *Application Dictionary → Process Definition → Validate Picking List →
Custom Component* on **2026-08-19**, and the process was confirmed working against the live client.

## Current code (verbatim from `etendodev`, unchanged by this migration)

### `em_etmeta_onload`

Runs on the custom-component path, which passes a **reduced sandbox** —
`{ callAction, fetchDatasource, OB, fetch: undefined }`, with no `Metadata`, `messageBar`, `confirm`,
`callDatasource` or `BigDecimal`. This script only uses `callAction` and `OB.PropertyStore`, so it is
consistent with that context.

Two details worth not "correcting" later:

- **`_topLevel: true` is required here.** `ValidateActionHandler` reads `recordId` and `action` from the
  **root** of the request body, not from `_params` — confirmed in its constant pool, and matching
  Classic, which calls it with a flat `{recordId, action}` payload (`OBWPL_Process.js:85-88`). The
  `em_etmeta_onprocess` script below deliberately omits the flag because `ManagePickingListAction` *does*
  read `_params`. The docstring of `createCallAction` (`warehouseApiHelpers.ts:30-34`) names
  `ValidateActionHandler` as the reason the flag exists.
- **The `processId` passed is the process's own id.** Classic sends no `processId` for this call, so the
  kernel default applies; passing the launching process's id is equivalent.

```js
async (_processDefinition, { selectedRecords }) => {
  const recordId = selectedRecords?.[0]?.id;
  if (!recordId) throw new Error("No record selected");

  const showUOM = OB.PropertyStore.get("UomManagement") === "Y";
  const exactAttr = OB.PropertyStore.get("ETAWIM_PickingExactAttributeValidation") === "Y";
  const showBoth = !exactAttr;
  const showOperative = showBoth || showUOM;
  const showQuantity = showBoth || !showUOM;
  const useOperativeQty = showUOM && exactAttr;

  const getOperativeQty = (line) => Number(line.operativeQty ?? line.operationQty) || 0;
  const getBaseQty = (line) => (useOperativeQty ? getOperativeQty(line) : Number(line.quantity) || 0);

  const response = await callAction("org.openbravo.warehouse.pickinglist.ValidateActionHandler", {
    processId: "40317268E74C445FA85DB97249AFFE37",
    action: "validate",
    recordId,
    _entityName: "OBWPL_pickinglist",
    _topLevel: true,
  });

  if (!Array.isArray(response.data)) throw new Error("No data returned from ValidateActionHandler");

  const lines = response.data.map((r) => ({
    ...r,
    quantity: Number(r.quantity || 0),
    operationQty: Number(r.operationQty || 0),
    qtyVerified: Number(r.qtyVerified || 0),
    qtyPending: Number(r.qtyPending ?? getBaseQty(r)),
    productId: String(r.productId || ""),
    shipmentLineId: String(r.shipmentLineId || r.inOutLineId || r.mInOutLineId || r.lineId || r.id || ""),
    scannedInputs: [],
  }));

  return {
    type: "warehouseProcess",
    titleKey: "pickValidate.title",
    inputBar: ["qty", "barcode"],
    gridColumns: [
      { field: "barcode",           labelKey: "pickValidate.barcode",      align: "left"  },
      { field: "product",           labelKey: "pickValidate.product",      align: "left"  },

      { field: "storageBin",        labelKey: "pickValidate.storageBin",   align: "left"  },

        ? [
            { field: "auom",         labelKey: "pickValidate.auom",         align: "left"  },
            { field: "operationQty", labelKey: "pickValidate.operativeQty", align: "right" },

        : []),

        ? [{ field: "quantity",      labelKey: "pickValidate.qty",          align: "right" }]
        : []),
      { field: "qtyVerified",       labelKey: "pickValidate.qtyVerified",  align: "center", editable: true },
      { field: "qtyPending",        labelKey: "pickValidate.qtyPending",   align: "right" },
    ],
    features: {
      dynamicBoxes: false,
      calculateWeight: false,
      trackScannedInputs: true,
      useOperativeQty,

    initialData: { lines, boxCount: 1 },
    recordId,
  };

```

The visibility block (`showUOM` → `useOperativeQty`) is a **line-for-line transcription** of Classic
`OBWPL_ValidateComponent.js:418-423`. The only structural difference is that Classic declares all
columns and marks the conditional ones `hidden: !showOperative` / `hidden: !showQuantity`, whereas the
schema omits them outright — same rendered result.

`features` is the mirror image of the packing siblings: `dynamicBoxes: false` and
`calculateWeight: false` (no boxes, no weight in picking), and `trackScannedInputs: true`, which is the
flag that makes the component accumulate `scannedInputs` per line for `onProcess` to send back.

### `em_etmeta_payscript_logic`

A bare object literal, so `classifyPayscriptBody` classifies it as the PayScript **DSL** and
`registerPayScriptDSL` registers `onScan` in the rules registry. `onScan` is the one key the warehouse
component reads.

```js
({
  onScan: async ({ barcode, qty, lines, callAction }) => {
    const showUOM = OB.PropertyStore.get("UomManagement") === "Y";
    const exactAttr = OB.PropertyStore.get("ETAWIM_PickingExactAttributeValidation") === "Y";
    const useOperativeQty = showUOM && exactAttr;
    const getOperativeQty = (line) => Number(line.operativeQty ?? line.operationQty) || 0;

    const validLines = (lines || [])
      .map((l) => {
        const lineId =
          l.shipmentLineId ||
          l.inOutLineId ||
          l.mInOutLineId ||
          l.lineId ||
          l.id ||
          null;

        if (!lineId) return null;

        const baseQty = useOperativeQty ? getOperativeQty(l) : Number(l.quantity) || 0;
        const qtyVerified = Number(l.qtyVerified) || 0;

        return {
          lineId,
          shipmentLineId: lineId,
          attributeSetValueId: l.attributeSetValueId || null,
          productId: l.productId || null,
          quantity: baseQty,
          qtyVerified,
        };
      })
      .filter(Boolean);

    const response = await callAction(
      "org.openbravo.warehouse.pickinglist.action.ValidateBarcodeAction",
      {
        processId: "50D2EB7B24B44EA39C4735AC51CA8E0A",
        barcode,
        validLines,
        qty,
        entity: "MaterialMgmtShipmentInOutLine",
        _entityName: "OBWPL_pickinglist",
      }
    );

    const actions = Array.isArray(response?.responseActions) ? response.responseActions : [];
    const returnAction = actions.find((a) => a?.returnData) || {};
    const messageAction = actions.find((a) => a?.showMsgInProcessView) || {};
    const errorMsg = messageAction?.showMsgInProcessView?.msgText || null;
    const rd = returnAction?.returnData || {};

    const shipmentLineId = rd?.shipmentLineId || null;
    const conversionRate = Number(rd?.conversionRate || 1);
    const scannedCode = rd?.scannedBarcode || barcode;
    const aiId = rd?.aiId || null;
    const algorithmId = rd?.algorithmId || null;

    if (shipmentLineId) {
      return {
        matchField: "shipmentLineId",
        matchValue: shipmentLineId,
        qty: qty * conversionRate,
        scannedCode,
        aiId,
        algorithmId,
      };
    }

    return { error: true, message: errorMsg || undefined };
  },
});
```

Every field read from `returnData` — `shipmentLineId`, `conversionRate`, `scannedBarcode`, `aiId`,
`algorithmId` — is emitted by `ValidateBarcodeAction`, confirmed in its constant pool. The return shape
matches `OnScanResult` / `OnScanError` in `types.ts`, including the optional `scannedCode` / `aiId` /
`algorithmId` triple and the optional error `message`.

Note that `qty` and `entity` are sent but do **not** appear in `ValidateBarcodeAction`'s own constant
pool; the quantity maths is done client-side (`qty * conversionRate`). They are harmless extras — the
barcode hooks (`ValidateBarcodePickingHook`) may consume them — and were left untouched.

### One Classic behaviour that is intentionally not carried over

Classic wraps every `pickingHandlerCall` in a confirmation prompt:

```js
// OBWPL_Process.js:131
isc.confirm(OB.I18N.getLabel(confirmMsg), function (clickedOK) { … });   // 'OBWPL_ProcessConfirm'
```

The migrated `onProcess` posts directly. This is a **substrate** property, not a choice made for this
process: the reduced warehouse sandbox has no `confirm`, and `GenericWarehouseProcess` substitutes a
different safeguard — `handleProcess` (`GenericWarehouseProcess.tsx:408-419`) refuses to process while
any line still has `qtyPending !== 0`, showing a blocking dialog instead. So the user cannot process a
half-verified list, which is the risk the Classic prompt was guarding against. The trade is a
*validation* gate rather than a *confirmation* gate; carrying the prompt across would need a sandbox
addition and is not proposed here.

**Verified non-issues** — recorded so nobody re-audits them:

- **The `iconStatus` column is not lost.** Classic renders a 10th column with a success/error/blank icon
  derived from `qtyPending` (`OBWPL_ValidateComponent.js:564-587`). The schema omits it, but
  `GenericWarehouseProcess.tsx:554-556` reimplements the same indicator from the same field.
- **The load-time `qtyPending` is equivalent.** Classic computes `baseQty - record.qtyVerified` at render
  (`OBWPL_ValidateComponent.js:534-536`) while the `onLoad` computes `getBaseQty(r)`. These agree
  because verification is per-session: there is no persisted verified-quantity column on `m_inoutline`,
  and `getGridData` emits `qtyVerified` as a literal `0`.

**Cosmetic difference:** Classic titled the popup `OBWPL_PickingList - <record identifier>`
(`OBWPL_Process.js:75`); the schema uses the static `pickValidate.title` ("Pick & Validate"), with no
record identifier. Same as both packing siblings.

### Two advisories for follow-up (neither blocks this process)

1. **The backend's error text is swallowed on load.** `ValidateActionHandler` returns
   `{message: {severity, text}}` when it cannot build the grid (e.g. `OBWPL_NoLines`), and Classic shows
   that text (`OBWPL_Process.js:71-74`). The `onLoad` instead throws a fixed string. `useWarehousePlugin`
   *does* surface a thrown `Error.message` to the UI (`useWarehousePlugin.ts:135-137`), so this is a
   one-line improvement in the `em_etmeta_onload` column, not a code change:

   ```js
   if (!Array.isArray(response.data)) throw new Error(response.message?.text || "No data returned from ValidateActionHandler");
   ```

   Left unapplied because the shipped script is working and this report does not rewrite working code.

2. **A packing label leaks into the picking dialog.** `GenericWarehouseProcess.tsx:413` hardcodes
   `t("packing.pendingToPack")` ("All items must be fully packed before generating…") for the
   pending-lines dialog. The locales already carry `pickValidate.pendingToValidate` ("All items must have
   verified quantities before processing…") in both `en` and `es`, and **nothing references it** — it was
   written for this process. The component already solves the same problem correctly one line at
   `:675`, branching on `schema.features.trackScannedInputs` to pick between `pickValidate.process` and
   `packing.generatePack`; the general fix follows that precedent. This is client code and was not
   touched by this migration. The other hardcoded `packing.*` labels are either identical in wording
   between the two blocks or belong to box/weight controls that this schema does not render
   (`dynamicBoxes: false`, `calculateWeight: false`, `inputBar` without `boxSelector`/`addBox`/
   `checkCalculate`).

### One timing note for QA

`isCustomComponent` is derived from the `processDefinition` **state**, which starts as the cached window
metadata and is replaced when the live `meta/process/<id>` response lands. If the cached copy lacks the
flag, the first render classifies the process as standard and only the second render mounts the
component. This is cosmetic (a possible flash of the empty dialog), not a correctness issue, but it is
the thing to watch if the dialog ever looks wrong for an instant on open.
