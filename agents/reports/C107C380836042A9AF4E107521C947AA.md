`hotfix/ETP-4643` to establish whether that code actually runs.

### Verdict: **works as-is — no change required**

`em_etmeta_onload` returns `_dynamicParameters`, a **supported** contract: the parameters are synthesized
at open time and rendered by the standard parameter form
(`utils/processes/definition/utils.ts:309, :630-648`). The process therefore presents a real dialog the
user fills in, then Execute posts it. That is the correct design here and needs no Manual-specific
mechanism.

### Why the onLoad signature is fine despite looking custom

The body is written as `async (_processDefinition, {{ selectedRecords }}) => …`, which is the
*custom-component* signature. It nevertheless works on the **standard** path, because the standard path
passes the `view` proxy as the second argument and the proxy **spreads `hookData` onto itself**
(`utils/processes/definition/scriptProxies.ts:1171`), so `view.selectedRecords` exists at the top level
and the destructuring resolves.

Both spellings are now guaranteed: `createViewProxy` attaches `hookData` **nested** as well
(`view.hookData.selectedRecords`) while keeping the spread, so this destructuring is no longer
load-bearing on an undocumented detail. The documented `async (process, view) => …` with
`view.hookData.selectedRecords` (Section 9.2.4) is still preferred for new work.

### Explicitly: do **not** add `directExecute`

`directExecute` skips the dialog. This process *needs* the dialog — the user picks an employee (and,
for multiple records, whether to group). Adding it would make the process unusable.

### One thing to confirm in QA

`em_etmeta_onprocess` hardcodes `queryParams: {{ processId: "B7B1D4F53D4249C5A10D3AD0865D909F" }}` —
the id of **Manage PickingList Action**, not of this process. That is intentional in the picking-list
module (the shared action handler is registered under that process), but it is the kind of literal that
breaks silently if the module is reinstalled with new ids. Test 5 covers it.

## Manual-test checklist

1. Open **Picking List**, select **one** record, launch this process. → A dialog appears with an
   **Employee** select populated from the server, and **no** *Group* field (single record).
2. Confirm the Employee select is preselected with the handler's `defaultValue`, and that the options
   show employee **names**, not ids.
3. Select **two** records from the **same** organization. → The dialog now also shows the **Group**
   checkbox.
4. Select **two** records from **different** organizations. → An error message appears
   (`OBWPL_MultipleOrgs`) and no dialog opens.
5. Complete the dialog and press Execute. → The picking list is assigned to the chosen employee and the
   grid reflects it. A 404/"process not found" here points at the hardcoded `processId` above.
6. Run with **no** selection. → The "You must select at least one record!" error appears.
