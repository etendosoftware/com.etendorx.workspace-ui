### `em_etmeta_onprocess` — `obuiapp_process`

```js
(process, view) => {
  const selectedRecord = view.hookData.selectedRecords?.[0];

  const screenWidth = window.screen.width;
  const screenHeight = window.screen.height;
  const popupWidth = screenWidth * 0.5;
  const popupHeight = screenHeight * 0.5;
  const left = (screenWidth - popupWidth) / 2;
  const upperMargin = (screenHeight - popupHeight) / 2;
  const windowFeatures = `width=${popupWidth},height=${popupHeight},left=${left},top=${upperMargin}`;

  const state = crypto.randomUUID();
  const userId = OB.User.id;
  const etrxOauthProviderId = selectedRecord.id;
  const encodedState = btoa(JSON.stringify({ state, userId, etrxOauthProviderId }));

  const baseURL = selectedRecord.authorizationEndpoint;
  const separator = baseURL.includes("?") ? "&" : "?";
  const url = `${baseURL}${separator}state=${encodedState}`;

  return { type: "openUrl", url, windowFeatures, closeModal: true };
}
```

## Advisories (non-blocking)

1. **`ETRXGetMiddlewareToken` (`3B85498FECA646F19AD0E5D416C36776`) shares this blocker** — it also reads
   `OB.User.id` (`ETRX_GetMiddlewareToken.js:17`) — but it has additional, independent blockers of its
   own. This unblock does **not** unblock that one; its report stays `blocked` as-is.
2. **The popup-blocked path improves once migrated.** Classic's `alert()` is a dead end: the user is told
   the popup was blocked and has no way to proceed. The platform's fallback banner gives them a click
   that works. Worth confirming in QA.
3. **`directExecute` + `closeModal: true`, not "no `directExecute`".** *(Revised — the original advisory
   argued the opposite, before the Open Swagger QA lessons existed.)* Classic never opens a dialog at
   all: the button click opens the popup and nothing else. `directExecute` reproduces that with no extra
   click, and `closeModal: true` dismisses the bare overlay right after — with no further use for it,
   since Classic doesn't linger on anything either. This combination (`directExecute` + `openUrl` +
   `closeModal: true`) was exactly what `EC673C215BAD4B13875323085B07F95D.md` (Open Swagger) shipped
   broken and then fixed at the substrate level twice: once so the popup-blocked banner is reachable
   with no chrome (`shouldRenderDirectExecuteOverlay` gated on `hasMessage`), and once so the
   programmatic close isn't refused by the same guard that stops a user from abandoning a running
   process (`performClose` vs `handleClose` split). Both fixes are already live, so this process gets
   them for free.

## Manual-test checklist

1. Open **OAuth Providers** (`ETRX_oAuth_Provider`), select a row with `authorizationEndpoint`
   configured, click **Get Token**. → The popup opens **immediately, with no Execute click**, centred on
   screen.
2. Inspect the popup's URL: the `state` query param, base64-decoded (`atob(...)` then `JSON.parse`),
   must be `{ state, userId, etrxOauthProviderId }` where **`userId` is the real `AD_User_ID` of the
   logged-in session** (compare against the `id` on the user's own profile, or against `AD_User` in the
   DB for that login) — this is the field the whole unblock was about.
3. Confirm the process modal/overlay **closes immediately** after the popup opens (no lingering spinner).
4. Force a popup block (browser setting) and confirm the platform's **"Open link"** banner appears
   instead of a dead-end `alert()`, and that clicking it opens the same URL.
5. Run with **no row selected** — Classic does not guard this either; confirm the new UI doesn't crash
   (e.g. `selectedRecord` is `undefined`, `selectedRecord.id`/`.authorizationEndpoint` would throw). If it
   does throw, that's a real gap Classic also has (`params.button.contextView.viewGrid
   .getSelectedRecords()[0]` is unguarded in `ETRX_GetToken.js:19` too) — report it rather than papering
   over it silently, since matching a Classic crash faithfully is different from introducing a new one.
6. **No regression:** run another Manual process that already reads other `OB.*` namespaces (e.g. an SII
   process using `OB.I18N`/`OB.RemoteCallManager`) and confirm it's unaffected — `OB.User` is a new key,
   nothing existing changed shape.

## Updates

### 2026-08-18 — unblocked: `OB.User` added to the shim (substrate, additive)

**What changed.** `OB.User = { id, name, userName }` is now part of the shared `OB` shim
(`packages/MainUI/utils/ob/obShim.ts`), sourced from the already-loaded session user
(`useUserStore((s) => s.user)`, threaded through `buildProcessScriptContext` →
`ProcessDefinitionModal.tsx`). Field names mirror the classic `OB.User` definition
(`user-info.js.ftl:20-55`) exactly; `id` is `AD_User_ID`.

**Why this scope and not more.** Grepped every classic Defined-Process script in the ERP for
`OB.User.<field>` usage: outside `OB.User`'s own definition file, **only `.id` is read, and only by this
process and `ETRXGetMiddlewareToken`** — every other `OB.User.*` field (`isPortal`, `userName`,
`csrfToken`, `clientId`, `roleId`, …) is used exclusively by core navigation/profile widgets, never by a
process script. `name`/`userName` were included alongside `id` because they come from the same
already-loaded `user` object at zero extra cost and complete the identity shape without adding a new
data source; `clientId`/`organizationId`/`roleId`/`csrfToken` were deliberately left out — nothing
migrated needs them today, and they'd be speculative surface added without a measured need (the project
convention set by the Sii Monitor parent-context fix: add what's measured, not what might be needed).

**Why this doesn't regress anything.** `OB.User` is a brand-new key on the `OB` object — no existing
namespace, method, or field changed shape. Every process already migrated (the SII family, Open Swagger,
the PSD2 pair, …) keeps reading the same `OB.*` surface it always did.

**This process is now `migrated`** (generated code above); `ETRXGetMiddlewareToken` is **not** — it has
independent blockers untouched by this change (Advisory 1).

Status stays `migrated` (not `qa-passed`) until the manual-test checklist above is run.
