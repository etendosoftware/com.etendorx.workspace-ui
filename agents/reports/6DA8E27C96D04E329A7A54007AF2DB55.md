## status: migrated (one-line onLoad added)

**Audit of an already-populated process.** This process arrived with code in its `em_etmeta_*` columns
(not produced by this migration run). It was audited against the live client on branch
`hotfix/ETP-4643` to establish whether that code actually runs.

### Verdict: **works, but shows an empty dialog — one line fixes it**

`em_etmeta_onprocess` is populated and correct; `em_etmeta_onload` is **empty**. Because this process has
**zero parameters**, `renderParameters()` returns `null`, so the user sees a dialog with a title, an
empty ~12rem body and an Execute button. Only after clicking Execute does anything happen.

Etendo Classic acts on the button click itself. The parity fix is to add the direct-execute `onLoad`
introduced with the Manual substrate (Section 9.2.1).

### Required change

### `em_etmeta_onload` — `obuiapp_process`

Currently empty; paste this:

```js
() => ({ type: "directExecute" })
```

Nothing else changes. `em_etmeta_onprocess` stays exactly as it is.

### Coverage of the existing `onProcess`

| Item | Status |
|---|---|
| `async (process, params) => …` reading `params.recordIds` | supported — the second argument is the view proxy, which spreads `hookData` (so `recordIds` resolves at the top level) |
| empty-selection guard returning `{ error: { msgText, msgType } }` | supported |
| `callAction('…ManagePickingListAction', { _buttonValue: 'DONE', _params: { pickinglist, action: 'close' }, _entityName: 'OBWPL_pickinglist' })` | supported — mirrors the classic stateless-action payload |
| returning the raw `response` so the modal reports the server message | supported |

### Two things to confirm in QA

1. `queryParams: { processId: "B7B1D4F53D4249C5A10D3AD0865D909F" }` is hardcoded to **Manage
   PickingList Action**, not to this process. Intentional in this module (the shared handler is
   registered there), but brittle across reinstalls.
2. The `onProcess` returns the whole `response`. Confirm the server actually nests a `message` where the
   modal looks for it, otherwise a successful run reports nothing.

## Manual-test checklist

1. **Before** the change: launch the process. → Confirm the empty dialog with an Execute button
   (documents the starting point).
2. Paste the `onLoad` above and reload the metadata.
3. Open **Picking List**, select one record, launch it again. → **No dialog body**: only a brief loading
   overlay, then the result. This is the Classic behaviour.
4. Confirm the server's message is reported and the grid refreshes so the new picking-list status shows.
5. Select **several** picking lists and run it. → All ids go in a single call.
6. Force a server rejection (a picking list in a state the handler refuses). → The error is shown and
   the modal comes back with its chrome so the message is readable and closable.
7. Run with **no** selection. → The "No picking lists selected" error appears instead of a call.
