### `em_etmeta_payscript_logic` — `obuiapp_process`

```js
// @module-scope
// Mirrors OB.RoleInheritance.recalculatePermissions + .execute
// (recalculatePermissionsProcess.js:53 and :27).
const ACTION_HANDLER = "org.openbravo.role.inheritance.RecalculatePermissionsHandler";
const TITLE_LABEL = "RecalculatePermissions";

// Classic picks one of three labels: template / plain role for a single selection,
// and a generic one for several. Kept as an if/else rather than chained ternaries.
const confirmationText = (roles) => {
  if (roles.length !== 1) return OB.I18N.getLabel("RecalculateMultipleRolesPermissions");
  const role = roles[0];
  const label = role.template ? "RecalculateTemplateRolePermissions" : "RecalculateRolePermissions";
  return OB.I18N.getLabel(label, [role.name]);
};

const recalculatePermissions = async (roles) => {
  const confirmed = await confirm(confirmationText(roles), {
    title: OB.I18N.getLabel(TITLE_LABEL),
  });
  if (!confirmed) return { type: "closeModal" };

  const response = await callAction(ACTION_HANDLER, {
    roles: roles.map((role) => role.id),
  });

  const message = response?.data?.message ?? {};
  return {
    message: { msgType: message.severity, msgTitle: message.title, msgText: message.text },
    responseActions: [{ refreshGrid: {} }],
  };
};

return { recalculatePermissions };
```

## Advisories (non-blocking)

1. **Severity mapping widened, deliberately.** Classic collapses everything that is not `success` into
   `TYPE_ERROR`. The migrated code passes the server severity through, so a `warning` from the handler
   now shows as a warning instead of an error. This is strictly more accurate; if bug-for-bug parity is
   required, replace `message.severity` with `message.severity === "success" ? "success" : "error"`.
2. **`view.view.refresh()` → `refreshGrid`.** Classic refreshes the whole view ("refresh child tabs");
   the new-UI action refetches the launching tab's grid. The permission changes are on child tabs of
   the role, so confirm during QA that the reloaded record shows them (test 5).
3. **Undeclared global in the classic loop.** `for (i = 0; …)` at :56 leaks `i` to the global scope
   (only `isTemplate, message, messagetxt, name, selection, roles` are declared). The migration uses
   `map`, so the leak disappears.
4. **Empty-selection guard added.** Classic would post an empty `roles` array; the migrated code returns
   an error message. Deliberate, non-regressive deviation.
5. **Loading prompt dropped**: the modal already shows a pending state.

1. Open **Role**, select **one non-template** role, press **Recalculate Role Permissions**.
   → No empty dialog. The confirmation reads the `RecalculateRolePermissions` label **with the role's
   name interpolated**, and the dialog title is the `RecalculatePermissions` label.
2. Select **one template** role and repeat. → The confirmation text is the *template* variant
   (`RecalculateTemplateRolePermissions`), again with the name.
3. Select **two or more** roles. → The confirmation is the generic
   `RecalculateMultipleRolesPermissions` text, with no name interpolated.
4. Press **Cancel** on any of the above. → Dialog closes, no banner, no error, permissions unchanged.
5. Press **OK** on a role that inherits from a template. → Success banner, and the role's
   **child permission tabs** (Window Access, Tab Access, …) show the recalculated rows after the
   refresh — reload the record manually if needed and report whether that was necessary (advisory 2).
6. Force an error (e.g. a role whose inheritance is inconsistent). → The banner shows the server error.
7. Run with **no** selection. → Error message instead of a crash.

## Updates

### 2026-08-17 — first QA run: the server message was being swallowed (substrate fix)

QA reported the process works end to end, but the feedback is poorer than Classic: the new UI showed a
generic *"Process completed successfully"* toast instead of the handler's own message
(`{"severity":"success","title":"Permissions recalculated correctly for role System Administrator",
"text":"No new records added into the role accesses"}`), which Classic paints in the message bar
(`recalculatePermissionsProcess.js:32-36`).

Root cause, entirely in the substrate — **two independent holes**:

1. **The returned `message` was never read.** `extractResponseMessage`
   (`useProcessExecution.ts`) looked at `responseActions[].showMsgInProcessView`, then a root-level
   `severity`, then `error`, and otherwise fell back to the generic text. The AR-1 return shape
   `{ message: {…}, responseActions: [{refreshGrid:{}}] }` matched none of them, so **every** AR-1
   process landed on the fallback. Thirteen migrated reports return that shape.
2. **The title was hardcoded.** `showProcessToast` fixed the toast heading to
   `process.completedSuccessfully` / `process.warning`, and `renderResponse` fixed the banner heading to
   `process.processError`, so `msgTitle` had nowhere to land even once it was read.

Fixes (client, additive): new pure reader `readReturnedMessage`
(`components/ProcessModal/utils/processReturnMessage.ts`) accepting both the script spelling
(`msgType`/`msgTitle`/`msgText`) and the raw handler one (`severity`/`title`/`text`); a new branch in
`extractResponseMessage` that consults it after `responseActions` and before the root-level `severity`;
an optional `title` on `showProcessToast`; and `readBannerTitle` feeding the two in-modal banner
headings. Absence of a message keeps every existing default text, so no other process changes.

**The generated code below is unchanged and needs no re-paste** — advisory 1 (severity passed straight
through) now takes effect as written. The same fix repairs the other 12 reports that return `message`.

Status stays `migrated`: the manual-test checklist has not been re-run to completion yet.
